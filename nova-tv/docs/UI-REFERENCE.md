# What a user-friendly UI looks like — nova-tv

This describes the target, in enough detail to build from and to review against.
It is a companion to `UI-PLAN.md`: that document decided *which* engines and
sources; this one decides what the user actually sees and feels.

---

## 0. The constraint that decides everything

A TV is not a phone with a bigger screen.

| | Phone | TV |
|---|---|---|
| Input | 10 fingers, direct touch | ~5 buttons, indirect |
| Distance | 30 cm | 3 m |
| Precision | per-pixel | per-focus-target |
| Interruption | constant | a session |
| Mistake cost | tap again | press BACK, lose your place |

**Every rule below is a consequence of that table.** Nobody hovers on a TV.
Nobody scrolls with a flick. If focus is not visible, the user is lost — there
is no cursor to fall back on.

---

## 1. The five rules that actually decide "friendly"

Everything else is decoration. These are the ones users feel.

1. **You always know where you are.** One focused element, always visible, never
   ambiguous. If two things look focused, the UI is broken.
2. **You always know how to leave.** BACK closes exactly one surface. It never
   exits the app while a sheet is open. No screen is a one-way door.
3. **Nothing is a lie.** No button to nowhere. No spinner that outlives its
   request. No "12 titles" that renders 3. No empty grid where a message belongs.
4. **It reacts before you doubt it.** Focus moves in **120ms**. Beyond that the
   D-pad feels sticky, and the user presses again — which overshoots.
5. **It never shouts.** One accent colour. One emphasised thing per screen. A TV
   is viewed for two hours; a UI that shouts is exhausting by minute ten.

Rule 3 is the one AI-generated UIs break most, and the one with a script
attached: `scripts/check_buttons.py` fails the build on it.

---

## 2. The distance test

Everything is designed to be read from 3 metres, which is roughly a 55" screen
at 1080p. That sets hard floors:

| Element | Minimum | Why |
|---|---|---|
| Body text | **18sp** | below this it renders as texture, not words |
| Title text | **24sp** | must be readable while scanning, not reading |
| Screen heading | **34sp** | the anchor that says "you are in Movies" |
| Poster card width | **140dp** | smaller and you cannot tell covers apart |
| Touch/focus target | **48dp** | the D-pad needs a target as big as a fingertip |
| Contrast (body) | **4.5:1** | 7:1 for muted text on gradients |
| Safe margin | **48dp** | TVs overscan; content inside the edge gets cut |

A phone layout scaled up fails the distance test at text and at focus targets,
in that order.

## 3. The palette, and why each colour exists

From `UI-PLAN.md` §3 — six colours, one accent, no exceptions:

```
background   #0B0E14 → #111827   vertical gradient, very subtle
surface      #151A24             the rail, sheets, cards
surfaceHigh  #1C2230             one step up: focused card fill
accent       #4C8DFF             blue — focus, primary action, selection ONLY
textPrimary  #F5F7FA             near-white
textMuted    #98A2B3             metadata: year, runtime, rating
```

Two deliberate choices worth stating, because they are the difference between
"clean" and "cheap":

- **`#F5F7FA`, not `#FFFFFF`.** Pure white on a dark background haloes on LCD
  panels at distance — the text appears to glow and the shapes behind it muddy.
- **Blue means "you are here" or "this is the action".** If blue is ever
  decoration, it stops being a signal, and the focus ring stops working.

### What is deliberately absent

No purple. No violet gradient. No teal. A saturated purple-to-blue gradient is
the single most recognisable "generated by an AI" tell in 2024–2026 UI, and it
is the first thing a designer notices.

---

## 4. Shape and depth: the three-value rule

```
12dp   cards, buttons, posters
18dp   sheets, drawers, overlays
999dp  pills (chips, tags, the selected filter)
```

That is the complete list. **Zero borders.** Separation comes from one step of
surface lightness (`#151A24` → `#1C2230`), never from a 1dp outline — outlines
at distance read as scratches.

The "engineered look" people dislike comes from a stack of small decisions: six
radii, mixed shadows, a border *and* a shadow *and* a gradient on the same card.
Removing all three is the whole fix. The only permitted hairline is the 1dp
accent on the focused element.

## 5. Focus: the one thing that must be perfect

```
rest      fill #151A24   no ring           scale 1.00
focused   ring 2dp #4C8DFF + 8dp glow     scale 1.04
pressed   fill #1C2230  ring 2dp          scale 1.00
```

- The glow uses `accentSoft` (accent at 18%) so it reads as light, not as a
  second border.
- Scale 1.04 and no more: at 1.10 the row visibly reflows as you scroll past.
- **120ms, and it must be interruptible.** Holding right must not queue five
  animations.
- In a horizontal row, the focused card **scrolls to 40% from the left edge**, not
  to centre. Centring means the next card is always half-hidden and the row
  feels like it is fighting you.

**Every focusable element has a focused state. No exceptions.** This is rule 1
expressed as an implementation constraint.

## 6. Screen anatomy

### 6.1 The shell

```
┌─────────┬──────────────────────────────────────────────┐
│ NOVA    │  Movies                                      │  ← 34sp, the anchor
│         │                                              │
│ ▸ Home  │  Continue watching                           │  ← 18sp muted
│   Movies│  ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐          │
│   Series│  │▓▓▓▓│ │    │ │    │ │    │ │    │          │
│   Anime │  └────┘ └────┘ └────┘ └────┘ └────┘          │
│   Search│                                              │
│         │  Recently added                              │
│ ─────── │  ┌────┐ ┌────┐ ┌────┐                       │
│ Settings│  │    │ │    │ │    │                       │
└─────────┴──────────────────────────────────────────────┘
   88dp                      48dp safe margin
   (icons)
```

- Rail is **88dp collapsed** — icons only. It expands to **220dp** on focus, and
  collapses the moment focus leaves. Content gets the screen; the rail yields.
- Rail labels appear on expand, not always: a permanently labelled rail steals
  12% of a 1080p screen for six words.
- The selected route is a **pill** (999dp) in `accent @ 22%`, not a border and not
  a full-width highlight bar.

### 6.2 The poster card — five states

The card is the most-repeated element in the app, so all five states are defined
once and used everywhere:

```
rest         poster, title in textPrimary 18sp, one line, ellipsised
focused      2dp accent ring, 8dp glow, scale 1.04
pressed      fill #1C2230, ring held, no scale
loading      surface fill, no spinner — a shimmer band, 1.2s, reduced-motion aware
unavailable  poster at 40% opacity + "Not available" in textMuted, still focusable
```

**Unavailable stays focusable.** Removing it from the row would silently change
positions as sources resolve, and the user's thumb-memory breaks. Dimmed and
labelled is honest and stable.

Below the poster, **two lines maximum**: title, then `year · runtime · rating`.
Anything longer is truncation, not design.

### 6.3 The detail surface

```
┌──────────────────────────────────────────────────────┐
│  ▓▓▓▓▓▓▓▓  THE TITLE                        34sp     │
│  ▓▓▓▓▓▓▓▓  2024 · 1h 48m · ★ 7.8 · Action            │
│  ▓▓▓▓▓▓▓▓                                            │
│  ▓▓▓▓▓▓▓▓  [ ▶ Play ]  [ + Watchlist ]  [ ⤓ ]        │
│                                                      │
│  A two-line description, clamped. The rest lives     │
│  behind "More".                                      │
│                                                      │
│  Sources  ● Addon A  ● Addon B  ○ Addon C            │
└──────────────────────────────────────────────────────┘
```

- One primary action, visually dominant. Secondary actions are outlined or
  text-only, never equally loud — **two equal buttons is the same as no primary
  button.**
- The source dots are real state: filled = answered, hollow = no result,
  pulsing = still asking. This is where "nothing is a lie" becomes visible.
- Description clamps at two lines. An unclamped synopsis pushes Play off-screen.

### 6.4 The player chrome

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│                  (video, full bleed)                 │
│                                                      │
│  ──────●─────────────────  00:42 / 1:48   ⚙  ⤢      │
└──────────────────────────────────────────────────────┘
```

- Chrome **auto-hides after 3s** of no input and returns on any key. Persistently
  visible chrome on a TV is a light leak.
- The scrubber shows buffered ranges in a lighter track. A scrubber that lies
  about buffering is why people mistrust video players.
- Controls are **focus-reachable**, not touch-only. On a TV the progress bar is
  navigated with left/right; it is a focus target, not a drag target.

### 6.5 The three states everyone forgets

These are where most apps feel broken, and they cost almost nothing:

| State | Looks like | Never |
|---|---|---|
| **Loading** | shimmer skeletons in the real card shape | a centred spinner on a black screen |
| **Empty** | centred icon + "No movies yet" + one action | a blank grid |
| **Error** | "Couldn't reach Addon B" + `Try again` + which source failed | "Something went wrong" |

The skeleton matters: it reserves the exact layout, so content does not jump
when it arrives. Jumping content on a TV reads as a bug.

The error message names **which source** failed and offers exactly one retry.
Vague errors cost the user a support cycle; specific ones cost them nothing.

## 7. Motion, and when to remove it

| Event | Duration | Easing |
|---|---|---|
| Focus change | 120ms | linear — easing here reads as lag |
| Card enter | 180ms | decelerate |
| Drawer open | 220ms | decelerate |
| Drawer close | 180ms | accelerate |

`reduceMotion` in `SettingsStore` sets **all durations to 0 and disables scale**.
Not "shorter" — zero. A user who sets that flag is telling you motion makes the
app unusable for them, and a token 50ms is still unusable.

## 8. The AI tells — what this UI must not look like

Called out explicitly because they are the default output of generated UI, and
the user asked for them to be avoided:

| Tell | Why it reads as fake |
|---|---|
| Purple/violet gradient | the 2024–2026 generator default; instantly recognisable |
| Border **and** shadow **and** gradient on one card | compensating for unclear hierarchy |
| Six or more corner radii | nobody chose them; they accumulated |
| Emoji as interface icons (🎬 🔍 ⚙) | renders differently per TV, sized inconsistently, not focusable |
| Generic filler ("Welcome back, User!") | says nothing, takes a screen |
| Grey boxes labelled "image" that never resolve | a promise the app does not keep |
| A button that looks pressed but does nothing | the thing `check_buttons.py` exists to catch |
| Identical 3-column grids for every content type | posters are 2:3, backdrops 16:9 — forcing one shape crops faces |
| "Loading..." in the centre of an empty screen | admits the layout was not planned |
| Every section equally emphasised | if everything is important, nothing is |

The pattern behind all ten: **the UI says something the code does not do.** User-friendly
is, at bottom, honesty rendered in pixels.

## 9. Honest gap: spec vs. what is in the app today

This section exists because a design document that claims to describe the shipped
app is the exact hallucination this project has scripts to catch.

| Item | Spec | In the app today |
|---|---|---|
| Rail collapsed/expanded | 88dp → 220dp on focus | fixed **200dp**, always labelled |
| Rail radius | pill 999dp | `RoundedCornerShape(10dp)` |
| Background | `#0B0E14 → #111827` gradient | flat **`#0B0E11`** |
| Surface | `#151A24` | **`#161A1F`** |
| Accent | `#4C8DFF` | **`#5B8DEF`** |
| Text primary | `#F5F7FA` | **`#E8ECF1`** |
| Route switching | six distinct panes | **all six render `HomePane`** |
| Poster states | five defined | rest + focused only |
| Skeletons | shimmer in card shape | centred `CircularProgressIndicator` |
| Empty state | icon + message + action | not implemented |

Two of these are straight defects and already reported by the checkers:

- **Six routes, one pane.** `check_buttons.py` flags `unrouted-entries`: HOME,
  MOVIES, SERIES, SEARCH, ADDONS, SETTINGS can all be selected and nothing
  branches on `route`. Every entry shows the same screen.
- **Colour drift.** The theme file has its own five colours that do not match the
  plan by a small, deliberate-looking amount. That is worse than being obviously
  wrong — it survives review.

The remaining gaps are styling work, not redesign: three radii, one gradient,
one accent.

## 10. Acceptance — what "done" means here

The UI is user-friendly enough to ship when all of these are true:

1. `scripts/check_buttons.py` reports **0 findings** (no unrendered state, no
   unrouted entries, no empty handlers).
2. Every route renders a distinct pane, with a visible heading naming it.
3. Every focusable element shows a focused state within 120ms.
4. BACK from any surface returns one level, never to a black screen.
5. Loading, empty and error states exist for every network surface, and the
   error names the failed source.
6. Only the plan's six colours appear in `ui/theme/`.
7. Only three radii appear anywhere in the codebase.
8. No string in the UI refers to content the app does not have.

Items 1, 2, 5 and 8 are mechanically checkable, and 1 and 2 already have a
script. The test of this document is not that it is followed — it is that these
eight lines can be verified without reading the code.
