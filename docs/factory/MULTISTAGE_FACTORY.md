# The multi-stage factory

This repository builds the Savage Browser. It builds it with a pipeline, and the pipeline has a
front end that is not written here: a **sealed set of 72 imported factories** that runs first, hands
its plans to the conveyor belt, and can be lifted out again as one component.

```
written code ──▶ sealed factory set ──▶ conveyor belt ──▶ current factories ──▶ production
                 (72 imported)          (7 stations)      (factory 1-4)        (final product)
```

## The four parts, in the order they run

| #   | Part               | What it is                                                                | Where it lives                           |
| --- | ------------------ | ------------------------------------------------------------------------- | ---------------------------------------- |
| 0   | Sealed factory set | 72 imported factories, sealed and hash-verified, run before anything else | `sealed-factories/`                      |
| 1   | Written code       | This repository's own source: the browser, its tests, its gates           | `shell/`, `docs/`, `tools/`              |
| 2   | Conveyor belt      | 7 connected stations, each one a gate that can fail the run               | `scripts/conveyor_belt.js`               |
| 3   | Current factories  | The four factories that produce, debug, tool and release the APK          | `factories/`, `factory-2/`, `factory-3/` |
| 4   | Production         | The signed release artefact and its evidence                              | `factories/final-product/`               |

## Stage 0 — the sealed factory set

`sealed-factories/` is one directory. Inside it:

- `SEAL.json` — the manifest: every factory's repository, commit, licence, payload hash, and whether
  its content may be redistributed;
- `SEAL.sha256` — the hash of that manifest, so the manifest cannot be edited quietly;
- `payloads/<id>.tar.gz` — 72 deterministic archives of the vendored slice of each factory;
- `vendor/*.json` — the vendoring record: which files were taken, their hashes, and the detectors'
  notes. For blueprint-only factories the file _contents_ are not here at all;
- `licenses/` — the licence text of every factory that publishes one;
- `ATTRIBUTION.md` — who each factory is and on what basis it is included, generated by the sealer;
- `manifest/RUN-REPORT.json` — what happened the last time the set ran;
- `runs/<timestamp>/<id>/` — the artefacts each factory produced: `plan.json`, `prompt.md`, and
  `model-output.md` when a model answered.

`tools/factory/sealed_factory_runtime.py` opens it. Opening is verification first: every payload hash
is recomputed against the seal, and a single mismatch stops the pipeline instead of feeding it.

### What "operating" means here, exactly

Each factory is executed in two parts, and the second part depends on what the machine can actually
reach:

1. **Its definitions are read** from its own sealed files — the stages, workers, checks and prompt
   assets it ships, found by path, by declarative list keys, and by the words the files themselves
   use. This always happens.
2. **Its brief is sent to a model** — but only to a model that is genuinely reachable.

Reachability is detected, never configured:

| Preset                                                           | How it is found                                    | What it does                                                  |
| ---------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| `ollama`                                                         | TCP 127.0.0.1:11434 answers                        | `POST /api/generate`, model from `OLLAMA_MODEL` or `llama3.1` |
| `lmstudio`                                                       | TCP 127.0.0.1:1234 answers                         | OpenAI-compatible `chat/completions`                          |
| `vllm`                                                           | TCP 127.0.0.1:8000 answers                         | OpenAI-compatible `chat/completions`                          |
| `openai`, `groq`, `mistral`, `openrouter`, `anthropic`, `google` | the matching API key is already in the environment | that provider's own endpoint and a current default model      |

No key is written to disk, printed, or stored in any report — the report says _which_ provider was
used, never the credential. Nothing is installed and nothing is downloaded to make this work: a
machine with Ollama running needs no setup, and a machine with none of these still runs the whole
stage, in plan mode, and says so.

### The three statuses a factory can end a run with

| Status              | Meaning                                                                                                                                                                                                                                                                                               |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OPERATIONAL-MODEL` | Its plan and prompt were produced **and** a model answered; the answer is on disk                                                                                                                                                                                                                     |
| `OPERATIONAL-PLAN`  | Its definitions were read and its plan and prompt were produced; no model was reachable or the call budget was spent                                                                                                                                                                                  |
| `NO-STRUCTURE`      | The sealed slice holds no stage, worker or prompt definitions — the blueprint-only factories, whose definitions are code this component deliberately does not redistribute. No model call is made for these: there would be nothing for it to run, and a generic answer would be reported as progress |

Two more statuses exist for failures and are never softened: `MODEL-FAILED` (a provider was reached
and refused, with its own error text recorded) and `UNREADABLE` (a payload could not be opened, which
fails the stage). There is no status for "worked" — a run that did not happen says so.

The last run of this set, on this checkout: **372 stages, 252 workers, 93 checks, 450 prompt assets
and 2 429 published sections read from 43 factories**; 29 slices held no definitions; 0 unreadable; 0
invented. The 43 that ran and the 29 that did not are not a coincidence and not a threshold: the 29
are exactly the blueprint-only factories, the ones whose content this component may not carry. Every
factory whose content can be carried runs.

### Sealed and removable

The component is an _inert_ set: nothing in `shell/`, `factories/`, `factory-2/` or `factory-3/`
imports it, reads it, or names it. Deleting `sealed-factories/` leaves the repository building the
same browser with the same four factories, because station 0 of the belt is written to report

```
sealed component ABSENT - the belt continues with this repository's own factories
```

and continue. The exact removal list is recorded inside `SEAL.json` under `removal`, and
`shell/tests/test_sealed_factory_runtime.py` proves the list matches the files that exist — including
a test that copies the runtime into an empty tree and checks that absence is reported, exits zero,
and creates nothing.

## The conveyor belt, its seven stations

`scripts/conveyor_belt.js`, run by `node scripts/conveyor_belt.js`, `make conveyor` or the CI workflow:

| Station | Name                                | What must hold                                                      |
| ------- | ----------------------------------- | ------------------------------------------------------------------- |
| 0       | Sealed Imported Factory Set         | The seal verifies, the set runs, and every factory is accounted for |
| 1       | Sanitation & Hygiene                | EditorConfig, ignore rules, no secrets                              |
| 2       | Static Analysis & Schema Invariants | Contracts parse and schemas hold                                    |
| 3       | Accessibility & Quality Invariants  | axe-core / Lighthouse invariants                                    |
| 4       | Dead Code & Dependency Pruning      | Knip / Vulture find nothing to prune                                |
| 5       | Footprint & Sizing Checks           | size-limit budgets                                                  |
| 6       | AI Reviewer & Broker Hand-Off       | CodeRabbit rules and the anti-deception auditor                     |

Station 0 fails the belt for a tampered payload and for a partial report; it _does not_ fail for
absence. That asymmetry is the whole design: sealed plastic can be cut open or thrown away, but it
cannot be quietly resealed with something else inside.

## What the imported factories contributed

Two of the 72 — `AshishYesale7/LGFlutterStarterKit` and
`sch0penheimer/AWS-DevSecOps-Hybrid-Software-Factory` — vendored nothing at all until the slice
patterns learned where their definitions live (`skills/` and `.agent/` trees; `buildspecs/` phase
files), which is exactly the plug-and-work bar: a factory that cannot describe itself is not a factory
this pipeline can run. Both now carry slices, and all 72 do.

The 72 factories were catalogued in `docs/factory/IMPORTED_FACTORY_CATALOG.md`: 12 GitHub searches,
869 repositories seen, 90 verified by reading their tree and README, 72 kept because they matched at
least four of six factory characteristics, 48 of them carrying AI-worker code. 53 show AI-worker
evidence in the slices sealed here (providers or entrypoints in the vendored files). Their stage
structures
are read at every run, which is how the belt's own station list is held to the same shape the
industry actually uses — intake, workers, verification, revision, release.

The influence is design-level and recorded, not copied: for the 43 permissive-licence factories the
vendored files carry their licence and are hash-sealed in `payloads/`; for the 29 others not one byte
was taken, and the repository re-implements only what their published documentation describes.
`ATTRIBUTION.md` names which is which, per factory.

## Reproducing a run

```bash
python3 tools/factory/sealed_factory_runtime.py verify   # seal only
python3 tools/factory/sealed_factory_runtime.py status    # seal + what models are reachable
python3 tools/factory/sealed_factory_runtime.py run --max-model-calls 4
node scripts/conveyor_belt.js                            # station 0 among the rest
```

`--max-model-calls` caps the number of paid calls in one run; `--require-model` fails the run when
nothing was reachable, which is the honest switch to use in CI where a model _is_ expected.
